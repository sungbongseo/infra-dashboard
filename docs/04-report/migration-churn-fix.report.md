## Executive Summary

| 관점 | 내용 |
|---|---|
| **Problem** | Phase A 정밀 검증 시점에 발견된 1 failed (`migration.test.ts > detects churned customers`) — 1월 매출 → 2월 공백 → churned 감지 기대했으나 0건. 표면적으로는 알고리즘 버그로 보였으나, **실제는 알고리즘 정확 / 테스트가 비즈니스 룰 미반영**. `migration.ts:198-219` B2B 보정 로직(연속 3개월 미만 공백은 이전 등급 유지)이 의도적으로 1-2개월 단발 공백을 churn으로 안 잡음. 테스트가 이 비즈니스 룰을 반영하지 못함. |
| **Solution** | 테스트 시나리오를 비즈니스 룰에 맞게 수정 — "3개월 연속 매출 공백" 시 churn 감지로 변경. 추가로 B2B 보정 룰의 명시적 검증 케이스 3건 (1M / 2M / 3M 공백)을 신규 추가하여 비즈니스 룰을 코드+테스트로 이중 명시. **알고리즘 코드 변경 없음** (비즈니스 의도 정확히 반영 중). |
| **Function UX Effect** | 사용자 경험 변화 없음 — 알고리즘 동작 동일. 다만 회귀 방지 강화 — 향후 B2B 보정 룰이 의도치 않게 변경되면 새 테스트 3건이 즉시 감지. 비즈니스 룰("연속 3개월 공백만 churn") 명시적 문서화. |
| **Core Value** | 알고리즘과 테스트의 자기 일관성 회복 + 비즈니스 룰 이중 명시. **전체 단위 테스트 472/473 → 476/476 (🎉 100%) 도달**. Phase A 정밀 검증 완전 종결. 향후 migration 모듈 리팩토링 시 비즈니스 룰 보존 안전망 확보. |

## 4. 회고

### 무엇을 배웠나

1. **"테스트 실패 = 알고리즘 버그"가 아닐 수 있다** — 알고리즘 주석을 따라가니 비즈니스 룰이 명확. 표면적 수정이 아닌 *의도 분석*이 정답.
2. **B2B 보정 룰의 가치 재발견** — 단발 공백을 churn으로 잡으면 false positive 폭증. 현재 알고리즘이 비즈니스 현실 잘 반영.
3. **테스트가 비즈니스 룰을 명시한다** — 신규 3 테스트가 향후 리팩토링 시 안전망. 코드 + 테스트 = 이중 명시.

### 무엇이 쉬웠나

- Root cause가 코드 주석에 명시 → 진단 5분
- Fix scope가 작음 (테스트만, 알고리즘 0)
- /pdca plan으로 옵션 비교 후 사용자 결정 1회 → 실행

### 다음을 위한 인사이트

- 테스트 실패 시 *알고리즘 의도 vs 테스트 expectation* 양쪽 다 검토 필요
- 비즈니스 룰이 알고리즘에 박혀있을 때 → 명시적 검증 테스트로 안전망
